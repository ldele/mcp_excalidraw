# TICKETS — issues reported against mcp_excalidraw

One section per report, newest first (cpc ADR-047). A ticket is something somebody **reported** —
a consumer running a gate, a reader of a doc, a user of the app — and it is owed an answer. Open
one with `cpc-ticket new --title "…" --from "who (version) · date"`; close it with
`cpc-ticket close --id N --as fixed|declined|duplicate --note "where the answer went"`.
`cpc-ticket check` fails when this file stops being a ledger; `cpc-digest` lists the open ones.

Not a known issue: that is a weakness this project found in itself, logged the second time it bit
(`.claude/KNOWN_ISSUES.md`). A ticket may become one, or a fix, or a deliberate no — the
`Resolution` line says which. Nothing here is rewritten or deleted; a declined ticket keeps its
reason.

The first five are the findings of one consumer's session, filed from
`docs/feedback/2026-08-21-provenote-wireframe-session.md` (its §1–§5) the day the ledger was
created; the vendored cpc (1.8.0) predates `cpc-ticket`, so until the next re-vendor the verbs
run from the global install: `cpc-ticket --root . …`.

## T-015 — Any origin can read, change and wipe a running canvas; a write through sync is logged as a person's
- **Status:** fixed · 2026-10-08
- **From:** Scribe agent session, while reading the npm advisories (1.3.0) · 2026-10-08
- **Symptom:** src/server.ts line 62 is app.use(cors()) with no options, and nothing checks Origin or Host, on HTTP or on the WebSocket. Every route answers Access-Control-Allow-Origin: * and the preflight approves PUT and DELETE. Seen on main at b3a6f81 with Origin https://attacker.example: GET /api/elements, /api/files, /api/snapshots and /api/changes are readable; POST /api/elements, /api/elements/sync, /api/elements/from-mermaid and DELETE /api/elements/clear succeed; a text note added through sync is logged by human; a request with Host attacker.example is served; the WebSocket connects and receives initial_elements. In Chrome 154 a page on another loopback port and an HTML file opened from disk (origin null) read, write, open the socket and clear with no prompt; a public https site is blocked until Chrome's local-network-access permission is granted, and then does all four. Upstream at 96d9c21 has the same line (its issue 39, its open pull request 74).
- **Reproduce:** With a canvas on a private port: curl -i -H 'Origin: https://attacker.example' http://127.0.0.1:PORT/api/elements returns the scene with access-control-allow-origin: *, and curl -X DELETE with the same header on /api/elements/clear empties it. Scripts, untracked in the spare worktree C:/Projects/mcp_excalidraw-merge/tests/probe: cross-origin-http.mjs (raw HTTP and the socket) and cross-origin-browser.spec.mjs (Chrome, four page origins; run with PW_CHANNEL=chrome).
- **Note:** 2026-10-08 — Assessed, not fixed. Reach: the server keeps everything in memory and has no route that takes a file path or runs a command, so what is exposed is the canvas: read it (elements, embedded images, snapshots, the change log, the live socket), change it, wipe it, send Mermaid text to the open tab, and, specific to this fork, plant markup through sync that the change log attributes to a person, which the review loop tells an agent to act on. Who can: any page served from this machine or opened from disk, silently; a public website only once the owner allows Chrome's local-network prompt (Chrome 154; the prompt itself was not seen, automation cannot show it; Firefox and Safari not tested). Any local process can as well, and no origin rule changes that. Proposal, the smallest: one guard ahead of the routes that refuses a request whose Origin is present and is not the server's own, with an allow-list from the environment for npm run dev (its page is on port 5173); the same guard refuses a Host that is not a loopback name; the same test on the WebSocket upgrade; cors() dropped. About 25 lines in src/server.ts, which is upstream's file, and one check in the state script. The CLI, the MCP server and the canvas page send no foreign Origin and keep working. Upstream's pull request 74 restricts cors to an ALLOWED_ORIGIN and adds an optional bearer token, +550 -267 over 6 files, open since 2026-04-16 and conflicting; its cors line alone covers neither the socket, nor the Host header, nor requests that need no preflight. Whether to fix, and how, is the owner's.
- **Resolution:** DEVLOG 2026-10-08 (i). A guard ahead of every route and on the WebSocket upgrade (src/core/origin-guard.ts): a request is refused with 403 when its Origin is present and is neither the origin of the host it was sent to nor listed in CANVAS_ALLOWED_ORIGINS, or when its Host is not a loopback name while the server is bound to loopback. cors() no longer answers every origin. Check: requests from another site are refused, in scripts/check-state-integrity.mjs. In Chrome 154 the four page origins of this ticket are now blocked on read, write, socket and clear. Not authentication: a local program that is not a browser can still call the API.
